# A 与老师历史运行差异的 10 轮诊断实验

日期：2026-09-27

## 1. 目的与证据边界

已确认 A/B/C 的实际服务器启动脚本使用：

```text
/mnt/cache/wanghanzhi/envs/whu_mars/bin/python3
```

因此，“A 与老师使用同一 `whu_mars` 环境”不能再作为已知前提。两者使用
同型号 A800-80GB 硬件，只能排除明显的 GPU 型号差异；依赖环境和
`torch.backends.cudnn.benchmark` 仍是待拆分变量。

本轮只做 10 个 epoch 的机制诊断，回答三个问题：

1. D10：A 的 `whu_mars + benchmark=False` 能否在相同 seed 下复现早期轨迹；
2. E10：在 `whu_mars` 中只把 benchmark 改为 `True` 是否改变轨迹；
3. F10：在 E10 基础上把解释器改为 `llmpar` 后是否进一步接近老师历史轨迹。

10 轮结果用于定位差异来源，不用于宣称最终性能优劣，也不替代完整 60 轮实验。

## 2. 共同固定条件

- 单卡 A800-80GB，`CUDA_VISIBLE_DEVICES=0`、`WORLD_SIZE=1`；
- 同一诊断源码提交；
- 数据：`/mnt/cache/wanghanzhi/Datasets/WHU-MARS`；
- 初始权重：`/mnt/cache/wanghanzhi/Datasets/ViT-B-16.pt`；
- raw OpenAI CLIP ViT-B/16；
- CLIP native normalization；
- 原始 PKM，K=4、P=16；
- 逻辑 batch 64，三模态实际图片 batch 192；
- CE + soft-margin triplet；
- Adam，head LR `3.5e-4`，backbone LR `5e-6`；
- 100-update warmup、per-update cosine；
- `MAX_EPOCHS=60`，使前 10 轮 scheduler 轨迹与正式配方一致；
- `STOP_AFTER_EPOCH=10`，只运行 10 轮；
- `CHECKPOINT_PERIOD=10`、`EVAL_PERIOD=10`；
- `SEED=1234`；
- `R1_mAP_eval(metric=sysu, FEAT_NORM=yes)`；
- 从磁盘重新加载 `transformer_10.pth` 统一复评。

## 3. 三组对照

| 任务 | 配置 | Python | benchmark | 输出目录 |
|---|---|---|---:|---|
| D10 | `configs/D_A_repeat_benchmark_false.yml` | `whu_mars/bin/python3` | False | `diagnostic_e10/D10_whu_benchmark_false` |
| E10 | `configs/E_A_benchmark_true.yml` | `whu_mars/bin/python3` | True | `diagnostic_e10/E10_whu_benchmark_true` |
| F10 | `configs/F_teacher_env_benchmark_true.yml` | `llmpar/bin/python3` | True | `diagnostic_e10/F10_llmpar_benchmark_true` |

D10 与 E10 仅允许 `CUDNN_BENCHMARK` 和输出目录不同。E10 与 F10 使用相同
YAML；解释器和输出目录只由启动脚本改变。因此：

- D10 对 E10 估计 benchmark 影响；
- E10 对 F10 估计环境影响，但该差异是整套 Python/torch/torchvision/timm
  环境的联合效应，不能直接归因到某一个包；
- A/老师历史结果只作为轨迹参照，不与 10 轮结果混成正式最终性能表。

## 4. 服务器执行

服务器需要一份独立诊断检出目录：

```text
/mnt/cache/wanghanzhi/XK/WHU-Baseline-diagnostic
```

先单独执行预检：

```bash
bash /mnt/cache/wanghanzhi/XK/WHU-Baseline-diagnostic/server/preflight_diagnostic_e10_a800.sh
```

预检会记录两个解释器的可执行路径、Python、torch、torchvision、timm、CUDA、
cuDNN 和 GPU 信息，并分别做 CUDA backward smoke。`llmpar` 的 `pip check`
若非零会被明确记录，但因本实验正是诊断历史环境，不在预检阶段自动终止；训练
是否可运行仍必须由对应任务的正常首轮日志确认。

随后一次创建三个独立单卡任务，按以下顺序串行调度：

```bash
bash /mnt/cache/wanghanzhi/XK/WHU-Baseline-diagnostic/server/run_D_A_repeat_benchmark_false_a800.sh
bash /mnt/cache/wanghanzhi/XK/WHU-Baseline-diagnostic/server/run_E_A_benchmark_true_a800.sh
bash /mnt/cache/wanghanzhi/XK/WHU-Baseline-diagnostic/server/run_F_teacher_env_benchmark_true_a800.sh
```

每个脚本都会拒绝复用非空输出目录。三个任务必须前台运行；预检通过不等于训练
已接受，至少要看到 launcher 配置和首个正常 iteration。

## 5. 判读顺序

统一读取每组的 `eval_epoch10/eval_stdout.log`，并同时比较：

1. epoch 1、5、10 的 loss、学习率和训练内评测；
2. epoch-10 磁盘重载后的总 mAP/CMC；
3. 九个模态对指标；
4. 预检记录的依赖版本和 cuDNN 版本；
5. 是否出现 skipped optimizer step、NaN、数据量或每轮 iteration 数变化。

| 观察 | 可支持的结论 |
|---|---|
| D10 接近 A，E10 明显向老师移动 | benchmark 是候选主要因素 |
| D10 接近 A，E10 仍接近 D10，F10 向老师移动 | 环境差异更值得优先追查 |
| D10 已与 A 明显不同 | 即使 seed 相同也存在未控制差异，不能归因 benchmark |
| E10 与 F10 接近，但均不接近老师 | 继续检查历史源码状态、数据清单与日志对应权重 |
| 三组早期差异很小 | 10 轮证据不足；如仍需因果判断，再选择性跑完整 60 轮或多 seed |

“接近”先按完整曲线和九个模态对的共同趋势判定，不预设单一 mAP 阈值。单次
seed 的更高结果不能证明设置具有系统性优势。

## 6. 代码治理

- A/B/C 的权威代码状态固定为 `d0b1f09`；
- 诊断开关和 D10/E10/F10 文件只保留在 `diagnostic/env-cudnn-e10` 分支；
- 正式 `main` 通过可恢复的 revert 提交恢复为与 `d0b1f09` 内容一致；
- 不把诊断代码合并回正式 baseline，也不覆盖 A/B/C 既有输出；
- 诊断结束后无需删除该分支：它保留实验可复现性，但正式开发从 `main` 继续；
- 若以后确需复用 `STOP_AFTER_EPOCH`，应在新实验分支重新引入，不能默认污染
  正式 baseline。
